# Практика: чек-лист защиты Linux-сервера

> Перед изменением SSH и Firewall обязательно сохраняйте текущую сессию и проверяйте доступ из второго терминала.

## 0. Перед началом

- [ ] Убедиться, что есть доступ к консоли облачного провайдера на случай потери SSH.
- [ ] Открыть отдельную SSH-сессию и не закрывать её во время настройки.
- [ ] Уточнить дистрибутив и имя SSH-службы: обычно `ssh` в Debian/Ubuntu и `sshd` в CentOS-подобных системах.
- [ ] Выполнять изменения по одному шагу и проверять результат.

## 1. Проверить SSH-логи и наблюдаемость

Посмотреть журнал SSH:

```bash
sudo journalctl -u ssh
# На системах, где unit называется sshd:
sudo journalctl -u sshd
```

Найти успешные входы за последние сутки:

```bash
sudo journalctl -u ssh --since "24 hours ago" | grep "Accepted"
```

Следить за событиями в реальном времени:

```bash
sudo journalctl -u ssh -f
```

Посмотреть текущие пользовательские сессии:

```bash
w
```

Проверить время и синхронизацию часов:

```bash
timedatectl
```

Что искать в журнале:

- `Failed password` — неверный пароль;
- `Invalid user` — неизвестное имя пользователя;
- `Accepted` — успешный вход, который должен быть объясним.

Проверить, сохраняется ли журнал после перезагрузки, и сколько места он занимает:

```bash
journalctl --list-boots
journalctl --disk-usage
```

Если журнал существует только в рамках текущей загрузки, настроить постоянное хранение systemd-journal. Ограничить объём журнала в конфигурации journald, чтобы логи не заполнили диск.

## 2. Настроить автоматические обновления безопасности

Проверить наличие `unattended-upgrades`. В минимальной установке Debian при необходимости установить пакет и включить соответствующую настройку.

```bash
sudo apt update
sudo apt install unattended-upgrades
```

После установки обновлений выяснить, нужны ли перезапуски сервисов:

```bash
sudo needrestart
```

Не включать автоматическую перезагрузку без оценки последствий для работающих приложений. Убедиться, что обновлённые компоненты действительно перезапущены.

## 3. Создать обычного пользователя и ограничить sudo

Работать под обычной учётной записью, а административные действия выполнять через `sudo`.

Проверить разрешённые команды пользователя:

```bash
sudo -l
```

Посмотреть записи о действиях `sudo` в журнале:

```bash
sudo journalctl | grep sudo
```

Практические правила:

- не выдавать без необходимости полный `sudo` без пароля;
- выдавать только необходимые полномочия;
- удалять учётные записи бывших сотрудников, подрядчиков и временных пользователей, которым больше не нужен доступ.

## 4. Перейти на SSH-ключи

На клиентском компьютере создать ключ:

```bash
ssh-keygen
```

Скопировать открытый ключ на сервер:

```bash
ssh-copy-id user@server
```

Проверить вход по ключу в **новом терминале**. Только после успешной проверки переходить к настройкам SSH.

В конфигурации SSH задать ограничения (значения ниже — примеры директив, а не готовый файл для любой системы):

```text
PasswordAuthentication no
PermitRootLogin no
AllowUsers user
```

Проверить также файлы дополнительных настроек:

```text
/etc/ssh/sshd_config.d/
```

На облачном Ubuntu-образе проверить, не задаёт ли Cloud-Init `PasswordAuthentication yes` в одном из подключаемых файлов.

Проверить итоговую конфигурацию и синтаксис:

```bash
sudo sshd -t
sudo sshd -T
```

**Важно различать команды:**

- `sshd -t` проверяет корректность конфигурации и синтаксис;
- `sshd -T` выводит эффективные настройки, которые применит сервер.

После проверки перезапустить SSH-службу подходящей для дистрибутива командой. Текущую сессию не закрывать, пока новый вход не проверен.

Смена SSH-порта — необязательная мера для уменьшения фонового шума, а не замена ключам и ограничениям доступа.

## 5. Проверить сетевые порты и настроить Firewall

Посмотреть слушающие порты и адреса:

```bash
sudo ss -t
```

Проверить, какие службы доступны только локально (`127.0.0.1`), а какие слушают все интерфейсы (`0.0.0.0`). Если база данных или Redis нужны только локальному приложению, настроить их на прослушивание локального адреса.

Для UFW последовательность принципиальна:

1. Установить политику запрета входящих подключений по умолчанию.
2. Разрешить SSH.
3. Разрешить только необходимые порты сайта/приложения.
4. Лишь после этого включить UFW.

Пример типовых команд UFW (порт SSH и список разрешённых портов нужно адаптировать под сервер):

```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp
# Добавить необходимые порты приложения, например HTTP/HTTPS:
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

Если SSH работает на другом порту, разрешить именно его до включения Firewall.

В облаке дополнительно проверить Security Groups / сетевой Firewall провайдера.

**Docker:** опубликованный порт контейнера может обходить обычные правила UFW. Если контейнер не должен быть доступен напрямую извне, привязать публикацию порта к `127.0.0.1`, например:

```bash
docker run -p 127.0.0.1:3000:3000 ...
```

## 6. Установить и настроить Fail2ban

Fail2ban анализирует журналы и блокирует IP после заданного количества неудачных попыток.

Настроить:

- порог неудачных попыток;
- временное окно подсчёта;
- длительность блокировки;
- `IgnoreIP` для доверенного офисного IP или VPN.

Пример: 5 неудачных попыток за 10 минут, блокировка на 10 минут. Это пример настройки, а не универсальное значение.

Если собственный адрес попал в бан, снять блокировку можно через `fail2ban-client` с действием `unbanip` и нужным IP. Точная команда зависит от jail и конфигурации.

Проверить, что Fail2ban действительно читает нужный журнал и обслуживает нужные jail.

## 7. Защитить секреты и историю команд

Найти файлы с приватными ключами и секретами, включая `.env`. Проверить права:

```bash
ls -l
```

Ограничить доступ владельцем:

```bash
chmod 600 /path/to/secret-file
```

Не передавать пароли в аргументах команд: они могут попасть в `.bash_history` и быть видны через список процессов (`ps`) во время выполнения.

Предпочтительнее использовать защищённый файл с правами `600` или подходящий механизм передачи через переменные окружения.

Если используется приём с командой, начинающейся с пробела, проверить настройку Bash:

```bash
echo "$HISTCONTROL"
```

Такое поведение работает при включённом `ignorespace` или `ignoreboth`; оно не гарантировано просто потому, что система — Debian или Ubuntu.

## 8. Организовать централизованный сбор логов

Развернуть отдельное хранилище логов и агент на каждом сервере. В рассматриваемом стеке:

- Grafana Alloy — агент сбора;
- Loki — хранилище;
- Grafana — интерфейс поиска и просмотра.

Отправлять:

- системный журнал;
- логи SSH;
- логи веб-сервера;
- логи приложения.

Продумать срок хранения: инцидент могут обнаружить спустя недели или месяцы. Для длительного хранения можно использовать объектные хранилища вроде S3.

Проверить права и учётные данные:

- агент может отправлять логи, но не должен иметь возможности удалять их;
- хранилище логов должно использовать отдельные credentials;
- компрометация сервера не должна автоматически давать возможность стереть централизованные логи.

## 9. Настроить метрики и алёрты

Развернуть Prometheus и Node Exporter. Собирать как минимум:

- загрузку CPU;
- использование памяти;
- заполнение диска;
- сетевой трафик.

Примеры сигналов:

- CPU долго загружен почти на 100% при отсутствии ожидаемой нагрузки;
- резко вырос исходящий трафик;
- диск быстро заполняется.

Настроить алёрты по метрикам и по логам. Вот три события:

- успешный вход по SSH;
- создание нового пользователя;
- прекращение поступления логов.

Передавать уведомления через Alertmanager в мессенджер или почту, которые регулярно проверяются.

Пример порога для CPU: загрузка выше 90% дольше 15 минут. Это иллюстрация, пороги нужно подбирать под конкретную нагрузку.

## 10. Порядок действий при подозрении на взлом

**Не перезагружать сервер и не удалять подозрительные файлы сразу.** Сначала сохранить сведения о процессе и восстановить хронологию.

1. Найти процессы, создающие нагрузку:

   ```bash
   top
   ```

2. Определить пользователя, от имени которого запущен подозрительный процесс.
3. В Loki найти события этого пользователя и восстановить цепочку: вход → загрузка файла → запуск.
4. Проверить попытки входа:
   - `Invalid user` часто является фоновым сканированием;
   - многочисленные `Failed password` для существующего пользователя могут указывать на целенаправленный подбор;
   - `Accepted` требует проверки.
5. Проверить задачи планировщика `crontab` всех пользователей.
6. Проверить все `authorized_keys` на сервере на наличие неизвестных ключей.
7. Если компрометация подтверждена:
   - изолировать сервер от сети, например через Security Group, сохранив доступ для расследования;
   - сделать снимок диска;
   - сохранить необходимые данные и доказательства;
   - пересобрать сервер с нуля;
   - заменить все пароли, ключи и токены, которые находились на сервере;
   - устранить первопричину на остальных серверах.

Удаление найденного майнера, cron-задачи и чужого ключа **не означает**, что сервер снова чист: неизвестно, какие ещё изменения мог оставить злоумышленник.

## Финальная проверка

- [ ] Логи SSH доступны через `journalctl`.
- [ ] Успешные входы можно быстро найти и объяснить.
- [ ] Время сервера синхронизировано.
- [ ] Журнал переживает перезагрузку и не может заполнить диск.
- [ ] Обновления безопасности устанавливаются автоматически.
- [ ] Администраторы работают под обычными пользователями через ограниченный `sudo`.
- [ ] SSH-вход по ключам проверен, парольный вход и root-вход отключены.
- [ ] Неиспользуемые учётные записи удалены.
- [ ] Базы данных и Redis не слушают внешние интерфейсы без необходимости.
- [ ] UFW и облачный Firewall разрешают только нужный трафик.
- [ ] Docker-порты проверены отдельно.
- [ ] Fail2ban настроен и не блокирует доверенные адреса.
- [ ] Секреты закрыты правами `600`, пароли не передаются в аргументах команд.
- [ ] Логи отправляются на отдельную систему с отдельными credentials.
- [ ] Метрики и алёрты работают, уведомления доходят.
- [ ] Есть понятный план расследования и реагирования на инцидент.

## Примечания к точности команд

- В расшифровке часть команд и путей была показана на экране, но не проговорена. Поэтому здесь они не восстановлены как точные, если их нельзя достоверно прочитать из текста.
- `sshd -t` — проверка синтаксиса конфигурации; `sshd -T` — вывод эффективной конфигурации. Это уточнение добавлено, потому что в автоматической расшифровке эти команды смешаны.
- Значения Fail2ban, пороги алёртов, SSH-порт и список открытых портов — примеры. Их нужно адаптировать к реальной системе.
