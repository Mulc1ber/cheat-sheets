# Теория: защита Linux-сервера

> Конспект «10 шагов защиты Linux-сервера». Сохранены логика и терминология материала; рекламные вставки исключены.

## 1. Почему сервер начинают атаковать почти сразу

Публичный сервер обычно начинают сканировать автоматические боты вскоре после появления в интернете. Они перебирают IP-адреса, ищут открытые порты и проверяют типовые сценарии:

1. Есть ли программа с известной уязвимостью.
2. Можно ли войти с простым или стандартным паролем.
3. Не доступна ли извне база данных или Redis без надлежащей защиты.

Если атака успешна, сервер могут использовать для майнинга криптовалюты, рассылки спама или участия в DDoS-ботнете.

**Абсолютной защиты не существует.** Новые уязвимости могут появляться и в хорошо известных программах. Поэтому безопасность строится из двух направлений:

- **Предотвращение:** закрывать известные уязвимости, ограничивать доступ и убирать лишние точки входа.
- **Обнаружение и расследование:** собирать логи и метрики, замечать подозрительные события и понимать, что произошло.

## 2. Десять шагов защиты

### Шаг 1. Научиться видеть, что происходит: логи

Первый шаг не закрывает уязвимость, а даёт наблюдаемость. Основной источник системных событий в современном Linux — журнал systemd, доступный через `journalctl`.

В SSH-логах важно различать:

- `Failed password` — неудачная попытка входа по паролю.
- `Invalid user` — попытка входа под несуществующим пользователем.
- `Accepted` — успешный вход. Каждое такое событие должно быть объяснимо.

Дополнительные признаки, заслуживающие внимания: вход в необычное время, неизвестный IP, неожиданный пользователь, подозрительное использование `sudo`.

Нужно также:

- знать, кто находится на сервере прямо сейчас;
- проверять синхронизацию системного времени;
- убедиться, что журнал сохраняется после перезагрузки;
- ограничить размер журнала, чтобы он не заполнил диск.

В Debian и Ubuntu имя systemd-unit SSH обычно `ssh`, в CentOS-подобных системах — `sshd`. Файл `/var/log/auth.log` зависит от настройки `syslog/rsyslog`; в Debian журнал может находиться только в `systemd-journal`.

### Шаг 2. Автоматически устанавливать обновления безопасности

Массовые атаки часто используют давно известные уязвимости, для которых исправление уже выпущено. Проблема — обновление не установлено.

В Debian и Ubuntu для автоматической установки обновлений безопасности используется `unattended-upgrades`.

- В Ubuntu Server пакет обычно установлен и включён.
- В минимальной установке Debian его может не быть — потребуется установить и настроить.
- Журналы обновлений помогают выяснить, что и когда было установлено.

Важный нюанс: установка обновления не всегда означает, что исправленная версия уже используется. Обновлённому ядру или библиотеке может потребоваться перезагрузка сервера или перезапуск соответствующего сервиса. `needrestart` помогает определить, каким сервисам нужен перезапуск. Автоматическую перезагрузку следует включать с учётом влияния на доступность приложений.

### Шаг 3. Работать под обычным пользователем, а не под root

Для повседневной работы создают обычную учётную запись и выдают ей необходимые права через `sudo`.

Преимущества:

- действия можно связать с конкретным пользователем;
- вызовы `sudo` записываются в журнал;
- права можно ограничивать конкретными командами и задачами.

Не следует без необходимости выдавать полный `sudo` без пароля: по сути, это почти эквивалент root-доступа. Если пользователю нужно перезапускать один сервис, права стоит ограничить этой операцией.

Неиспользуемые учётные записи (бывшие сотрудники, подрядчики, временные тестовые пользователи) нужно удалять: каждая оставшаяся запись — потенциальный путь входа.

### Шаг 4. Перейти на SSH-ключи и ограничить пользователей

Основные настройки SSH:

- отключить аутентификацию по паролю;
- запретить SSH-вход непосредственно под `root`;
- разрешить подключение только определённым пользователям через `AllowUsers`.

**Безопасный порядок действий:**

1. Создать ключ на клиентском компьютере.
2. Установить открытый ключ на сервер.
3. Проверить, что вход по ключу работает.
4. Только после этого отключить вход по паролю.

Есть нюанс конфигурации: SSH может подключать дополнительные файлы из `sshd_config.d`. На облачных Ubuntu-образах Cloud-Init может создавать файл с `PasswordAuthentication yes`. В описанном случае первое найденное значение имеет приоритет, поэтому настройка в конце основного файла может не сработать. Важно проверять итоговую конфигурацию, а не только содержимое одного файла.

Не закрывайте текущую SSH-сессию, пока не проверили новое подключение. Смена стандартного порта SSH уменьшает часть фонового шума в логах, но не является существенной мерой безопасности: целенаправленный сканер может найти и другой порт.

### Шаг 5. Проверить слушающие порты и настроить Firewall

Сначала нужно выяснить, какие службы слушают сетевые интерфейсы и на каких адресах.

- `127.0.0.1` — служба доступна только локально на самом сервере.
- `0.0.0.0` — служба слушает все IPv4-интерфейсы, в том числе потенциально внешний.

Базы данных и Redis, используемые только локальным приложением, не должны без необходимости слушать внешние интерфейсы. Сначала ограничивают адрес прослушивания самой службы, затем настраивают Firewall.

Принцип Firewall: **запрещать входящие подключения по умолчанию и явно разрешать только необходимые**.

Для Ubuntu рассматривается UFW. До его включения нужно разрешить SSH и необходимые порты приложения, иначе можно потерять удалённый доступ. В облаке дополнительно настраивают сетевой Firewall провайдера — Security Groups.

**Особенность Docker:** опубликованные порты контейнеров могут быть доступны извне, несмотря на правила UFW. Вот два варианта:

- публиковать порт только на `127.0.0.1`, если внешний доступ обеспечивает, например, Nginx;
- настроить ограничения в цепочке `DOCKER-USER`.

### Шаг 6. Ограничить перебор паролей с помощью Fail2ban

Fail2ban анализирует логи и считает неудачные попытки входа с каждого IP. При превышении заданного порога адрес временно блокируется через Firewall.

В качестве стандартного примера приведены пять неудачных попыток за 10 минут и блокировка на 10 минут. Параметр `IgnoreIP` позволяет исключить доверенные адреса, например офисный IP или VPN, чтобы не заблокировать себя.

Если SSH уже работает только по ключам, Fail2ban в основном уменьшает шум и лишнюю нагрузку от попыток входа. Для сервисов, где парольная аутентификация остаётся (например, почты или веб-панели), он может быть полезнее.

### Шаг 7. Защитить секреты и историю команд

Приватные ключи и файлы с секретами, например `.env`, должны быть доступны только владельцу. Права `600` и `644`: при `644` файл может читать любой локальный пользователь.

Не следует передавать пароли в аргументах команд:

- они могут попасть в историю shell;
- пока команда выполняется, её аргументы могут быть видны другим пользователям через список процессов.

Вместо этого секреты хранят в защищённом файле или передают подходящим способом через окружение.

Команду можно начать с пробела, чтобы Bash не записал её в историю. Это зависит от настройки `HISTCONTROL` (например, `ignorespace` или `ignoreboth`), а не гарантируется во всех системах по умолчанию.

### Шаг 8. Отправлять логи на отдельный сервер

Логи, которые хранятся только на взломанном сервере, злоумышленник с root-доступом может удалить. Поэтому их нужно отправлять на отдельную систему сразу после появления.

Примерный стек:

- **Grafana Alloy** — агент на сервере, который читает системные и прикладные логи;
- **Loki** — хранит логи;
- **Grafana** — интерфейс для поиска и просмотра.

Promtail — предшественник Alloy и с 2 марта 2026 года больше не поддерживается.

Рекомендации по организации логирования:

- отправлять не только SSH-логи, но и системные журналы, логи веб-сервера и приложения;
- хранить логи достаточно долго, чтобы расследовать инцидент, обнаруженный спустя недели или месяцы;
- агенту выдавать права на отправку, но не на удаление логов;
- не использовать для хранилища логов те же ключи и учётные данные, что и для самого сервера.

### Шаг 9. Собирать метрики и настраивать оповещения

Логи помогают понять, что произошло, но кто-то или что-то должно заметить событие вовремя.

Пример связки:

- **Prometheus** — собирает метрики;
- **Node Exporter** — отдаёт метрики сервера: CPU, память, диск и сеть;
- **Alertmanager** — отправляет уведомления по сработавшим правилам.

Возможные признаки компрометации:

- высокая загрузка CPU при отсутствии обычной нагрузки — возможный майнер;
- резкий рост исходящего трафика — возможная рассылка спама или участие в DDoS;
- быстрое заполнение диска.

Примеры событий, на которые предлагается настроить оповещения:

1. Успешный вход по SSH.
2. Создание нового пользователя.
3. Прекращение поступления логов с сервера.

Оповещения должны приходить в канал, который действительно проверяет администратор или команда: мессенджер либо почта.

### Шаг 10. Правильно реагировать на инцидент

Если сработал алёрт, не нужно сразу перезагружать сервер, удалять подозрительные файлы или завершать процесс. Это может уничтожить важные следы: откуда запущен процесс, от чьего имени и как он попал на сервер.

Последовательность расследования:

1. Посмотреть процессы и определить, что именно создаёт нагрузку и от какого пользователя запущено.
2. По логам восстановить, как этот пользователь вошёл на сервер.
3. Построить хронологию: вход, загрузка файла, запуск процесса.
4. Проверить `crontab` всех пользователей и все файлы `authorized_keys`: атакующий мог добавить задачу для повторного запуска вредоносной программы или собственный SSH-ключ.
5. Если компрометация подтверждена, считать сервер скомпрометированным целиком. Простое удаление майнера, задачи и ключа не доказывает, что система снова чистая.

Дальнейшие действия:

- изолировать сервер от сети, сохранив возможность дальнейшего анализа;
- сделать снимок диска и сохранить нужные данные;
- пересобрать сервер с нуля;
- сменить все пароли, ключи и токены, которые находились на сервере;
- устранить первопричину на остальных серверах.

## 3. Главная мысль

Защита — это не только запретить вход. Нужно выстроить полный цикл:

1. **Видеть:** собирать и сохранять логи.
2. **Предотвращать:** обновлять систему, ограничивать пользователей, SSH и сетевые порты, защищать секреты.
3. **Обнаруживать:** отправлять логи отдельно, собирать метрики и настраивать алёрты.
4. **Расследовать и реагировать:** сохранять следы, восстанавливать хронологию и при подтверждённой компрометации пересобирать сервер.

В финале ролика отдельно подчёркивается: если из десяти шагов сделать только два, это должны быть вход по SSH-ключам и отправка логов на другую машину.
